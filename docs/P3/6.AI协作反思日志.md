## 2. AI 助力分析（Q1）

本阶段 AI 最大的帮助是：**快速把 P1/P2 的需求和架构转化为可提交的详细设计初稿**。

具体帮助包括：

1. **降低从架构到详细设计的转换成本**  
   P2 已经确定了分层单体架构和 7 个核心模块，但如果人工从零设计类图、API 和数据库，需要反复整理模块边界。AI 能较快给出覆盖用户、任务、订单、支付、信用、后台管理的完整设计骨架。

2. **提高文档结构完整度**  
   API 文档中，AI 能自动补齐 URL、HTTP 方法、请求参数、成功响应、失败响应和错误码，使文档更接近前后端联调需要的格式。

3. **帮助发现设计层面的明显缺陷**  
   在 SOLID 检查中，AI 能辅助识别“上帝类”“服务接口过胖”“支付实现强耦合”“订单状态流转不集中”等典型问题，为人工修正提供线索。

4. **节省重复性文档工作**  
   ER 图、SQL、索引说明、API 示例响应等内容重复性较高，AI 能生成初稿，团队再集中精力审查核心设计是否合理。

预计节省时间：约 6-8 小时。

## 3. AI 误导分析（Q2）

SOLID 检查中发现的 AI 设计问题数量：**7 处主要问题**。

最严重的设计问题是：**AI 原始类图中 `OrderService`、`UserService` 和 `CampusHelperSystem` 职责过重，同时 `PaymentService` 直接依赖具体支付实现，导致模块边界模糊、后续扩展困难。**

### 3.1 具体误导点

| 问题 | 表现 | 人工修正 |
|---|---|---|
| 喜欢生成“大而全”的总控类 | `CampusHelperSystem` 同时管理用户、任务、订单、支付和后台 | 删除总控类，按 Controller/Service/Entity 分层 |
| 实体类承担过多业务流程 | `User` 中包含登录、发单、接单、评价等方法 | 实体类只保留属性和少量领域判断，流程放入 Service |
| 服务接口过胖 | `UserService`、`OrderService`、`AdminService` 方法过多 | 拆分为 `AuthService`、`TaskService`、`OrderService`、`PaymentService` 等 |
| 滥用继承 | 将 `ExpressTask`、`TutorTask`、`TeamTask` 设计为 `Task` 子类 | 改为 `TaskType + TaskValidationStrategy` |
| 支付强耦合 | `PaymentService` 直接依赖 `WechatPaymentClient` 和 `PointPaymentClient` | 抽象 `PaymentGateway` 接口 |
| 状态流转不清晰 | 订单状态由 `updateOrderStatus()` 直接修改 | 引入 `OrderStatusMachine` 集中校验 |
| 忽略学生项目落地约束 | 倾向生成复杂设计和过多模块 | 保留分层单体、MyBatis-Plus、Redis/定时任务等轻量方案 |

## 4. Prompt 改进计划（Q3）

### 4.1 上阶段改进措施的验证结果

P2 阶段提出的改进措施包括：给出明确约束、要求 AI 做减法、避免过度角色扮演。本阶段验证结果如下：

| P2 改进措施 | 本阶段验证结果 |
|---|---|
| 明确给出团队约束 | 有效。给出“4人团队、10周、Spring Boot + Vue、分层单体”后，AI 输出明显更贴近项目实际 |
| 要求 AI 做减法 | 有效。明确“不做微服务、不做复杂 IM、不做推荐算法”后，详细设计更可落地 |
| 多轮追问裁剪 | 有效。先生成 AI 原始类图，再做 SOLID 检查，最后修正，符合本阶段实验要求 |
| 谨慎使用角色扮演 | 部分有效。让 AI 扮演“务实工程师”比“资深架构师”更适合学生项目 |

### 4.2 本阶段新的改进措施

1. **先让 AI 输出“未修正版本”，再要求它审查自己**  
   这样可以更容易暴露 SOLID 问题，也符合 P3 的“AI 设计缺陷注入”要求。

2. **把 AI 设计和人工工程判断分开记录**  
   AI 原始类图保留问题，人工修正版说明修正理由，避免把 AI 输出直接当最终设计。

3. **要求 AI 输出可执行或可落地的内容**  
   例如数据库设计不仅要 ER 图，还要建表 SQL；API 不只列接口名，还要给请求/响应和错误码。

4. **在 Prompt 中明确“不要扩大范围”**  
   本项目不引入微服务、独立消息队列、复杂推荐算法和实时 IM，避免 AI 过度设计。

## 5. 本阶段的核心工程判断

决策内容：**在详细设计阶段保留“分层单体 + 领域服务拆分”的设计，不把任务类型做成复杂继承树，不让订单服务直接耦合支付、信用和通知细节。**

为什么 AI 无法做这个决策：

AI 能够生成完整类图、API 和 SQL，但它不知道团队真实的时间压力、成员技术熟悉程度和后续实现成本。AI 原始设计倾向于追求“看起来完整”，容易加入上帝类、过多继承和过度聚合的服务。作为架构负责人，需要根据 4 人团队、10 周周期和 P2 已确定的分层单体架构，主动控制复杂度。

本阶段最终选择：

1. `Task` 不使用多子类继承，而使用 `TaskType + TaskValidationStrategy`；
2. 订单状态由 `OrderStatusMachine` 集中控制；
3. 支付通过 `PaymentGateway` 接口隔离微信支付和积分支付；
4. 后台管理拆分为用户管理、订单管理、敏感词管理等服务；
5. 数据库保留必要日志表，例如 `order_status_logs`、`credit_logs`、`admin_operation_logs`，便于测试和追溯。

核心判断总结：

> 我们没有简单接受 AI 生成的“大而全”设计，而是根据 4 人团队、10 周周期、分层单体架构和 P0 功能优先级，保留核心实体与服务，拆分过重职责，并通过策略模式、状态机和支付网关接口降低后续变更风险。
